# Local engine setup integration

Server: instantiate `createEngineSetupService(baseAIConfig)` once per server. Expose GET `/api/engines/setup` → `service.status()`; POST `/api/engines/setup` with `{action:"rescan"}` → `service.rescan()`, or `{action:"reuse-auth",providerId:"codex",candidateId}` → `service.reuseLocalAuth(providerId,candidateId)`. Use existing same-origin/CSRF guards; reject all other body fields/actions. No browser executable/auth paths. GET discovery is credential-free; POST consent is explicit.

Pipeline: before `runPipeline`, obtain `await service.resolveConfig(providerId)` and pass that AIConfig into the existing pipeline AI config field (not a new engine implementation). It revalidates the selected executable and only supplies local auth after consent. Preserve trusted server advanced overrides. Session consent intentionally resets on server restart.

UI: `<EngineSetupPanel api={api} ready={ready} providerId={providerId} onProviderChange={setProviderId} />`. `api<T>(path:string, init?:RequestInit):Promise<T>` follows existing fetch wrapper. `ready` means server connection ready, not engine readiness. The panel performs discovery when connected, never inference. Parent should use setup status `engines.find(e=>e.providerId===providerId)?.ready` to disable analysis, via optional `onStatus` prop. Installed engines remain selectable even when incompatible; status explains blockers.

Contract implementation files: `src/server/engine-setup.ts`, `src/engine-setup-panel.tsx`. Detailed compatibility and auth limitations are recorded below as implemented.

## Implemented trust boundary and limits

- Host home is `os.userInfo().homedir`, not app-private HOME or browser input. Fixed native locations include ~/.local/bin, Homebrew, npm platform payloads and bounded (32 entries) owner/permission-checked ~/.nvm/versions/node. No PATH inheritance, shell profiles, nvm scripts, package.json execution or JS wrapper execution. Recognized Codex wrappers resolve to native payloads only. Unsupported/custom layouts require trusted server config.
- Discovery inspects local auth metadata only. Explicit reuse supports only the existing Codex `~/.codex/auth.json` allowlist. Mode must be private, owner must match, regular canonical file, bounded size. Content validation/copy stays in existing prepareAuth after isolation succeeds; no config/home/keychain copying, no token in browser state. Session consent resets on restart and executable-path change.
- Claude Keychain and local login extraction are deliberately unsupported. Existing trusted server `claude-oauth-token-file` (from official `claude setup-token`) or API-key file still work through the existing adapter; no invented token extraction. Codex Keychain-only logins are also not imported. The app never performs login or a global CLI install automatically.
- Installed, version, feature compatibility, auth, sandbox and inference verification remain separate. Native discovery can succeed while help or sandbox fails. Unsupported versions never silently relax flags. Ready requires authenticated status and runtime-verified isolation, not merely a found binary. Probe failure preserves the resolved installation identity.
- macOS policy is unchanged: macOS 26 ICU/system-policy incompatibility must remain unavailable until separately validated. Mac 26 startup evidence is not AI confinement evidence. No wildcard data grants or signing bypasses added.
- Linux credential-free preflights retain the existing minimized-environment native probe behavior; authenticated analysis remains gated by bwrap. Actual local setup run in this development container reported namespace/loopback EPERM and `ready:false` for both engines, with no unsandboxed fallback. No authenticated inference was run here.
- Official auth references reviewed: https://developers.openai.com/codex/auth/ (redirects to https://learn.chatgpt.com/docs/auth) and https://code.claude.com/docs/en/authentication . These document file/keychain storage alternatives and separately generated Claude setup tokens; they do not justify generic credential extraction.

## Optional Claude session token

Detected Claude installations offer a password input for an explicitly supplied official token. Run `claude setup-token` yourself in a terminal, then paste its result into **Claude setup token** and select **이번 세션에 토큰 사용**. This is not automatic login: a one-time manual setup-token step is still required. No advanced JSON/file editing, Keychain extraction, local OAuth refresh-token copying, or model call is performed by this form. [Official authentication guidance](https://code.claude.com/docs/en/authentication).

- Exact same-origin/CSRF-protected POST shapes: `{action:"set-session-auth",providerId:"claude",candidateId,token}` and `{action:"forget-session-auth",providerId:"claude",candidateId}`. No arbitrary paths, extra fields or other providers are accepted.
- The setup-token prefix and bounded 32 KiB ASCII token syntax are checked before writing; the existing `prepareAuth` adapter validates the private file. A random 0600 token file lives inside a service-owned 0700 temporary directory. The scratch-root override is trusted server/test injection only, never an HTTP field. It is not a persistent JSON setting, browser-storage value, log entry, or model-input field. The existing worker supplies `CLAUDE_CODE_OAUTH_TOKEN` only to the selected Claude process.
- Tokens are bound to the discovered candidate and its native executable fingerprint. Rotation, explicit **세션 토큰 삭제**, executable replacement/revocation, and normal app/server close remove token files and drop service references. Close aborts queued/ongoing work and cannot revive readiness or write a late file. JavaScript strings cannot promise secure memory zeroization. Forced process termination/power loss cannot promise normal cleanup; temporary files remain owner-private.
- The field clears before awaiting HTTP. UI errors are generic, and parent readiness clears on every setup request, including failed rotations. App text explicitly says **앱 종료 시 삭제**. A stored token does not prove authentication: readiness still requires the existing official status probe, supported CLI flags and verified isolation. Unsupported or inconclusive status remains unknown/not ready; no inference is attempted to guess authentication.
- Setup/status requests return 409 while an analysis is active, and new analysis returns 409 while setup is running. Existing analysis is not silently cancelled to change credentials.
- Existing trusted server advanced auth remains supported and is not overwritten by the form. Existing Codex reuse and lifecycle checks remain unchanged.
